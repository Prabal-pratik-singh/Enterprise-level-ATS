1. The big picture

This is an Applicant Tracking System (ATS): a tool companies use to receive job applications, read resumes, rank candidates and decide who to interview. It is designed like a system that must screen 500,000 applicants for one job, but it runs on one laptop with Docker Compose.

In one sentence: a resume is uploaded, then passed from one small service to the next through Kafka messages. Each service does one job (read the file, understand it, score it, check it for fraud, make it searchable) and writes its result to the database.

2. Foundations used by every feature

These are the building blocks that every feature relies on. Understanding them first makes the rest easy.

2a. Microservices + a shared library (ats-common)

LogicThe backend is a Maven "reactor" (one parent project with many modules). ats-common holds what everyone shares: database entities, the list of Kafka topics (Topics), the event format (EventEnvelope), the outbox, Flyway migrations, the LLM and embedding clients, the skill taxonomy. Each of the 8 services is its own Spring Boot app with its own Docker image.

WhyThe original plan was one application with an APP_ROLE switch. On 14 Aug 2026 it was converted, at the user's request, to real microservices so that each stage can be built, deployed and scaled on its own. A shared library avoids copying the same contract code eight times. Honest compromise: all services share one Postgres database. Giving each service its own data is the named next step for production.

Howbackend/pom.xml lists the modules; each Dockerfile builds with mvn -pl <service> -am. Every service's main class is in package com.ats so Spring finds the shared beans automatically.

Trap learned: adding a new module means adding a COPY <module>/pom.xml line to every Dockerfile, because the parent pom lists all modules and the build fails if one is missing.

2b. Kafka events

LogicEvery step publishes an event like resume.parsed. The next service listens to that topic. An event carries ids and storage keys only, never the file itself. The envelope is {event_id, event_type, occurred_at, application_id, job_id, data, schema_version}, and since C2 also subject_type (APPLICATION or PROFILE) + subject_id.

WhyIf the parser is slow, the uploads still succeed: messages simply wait in the queue. The waiting count ("consumer lag") is an honest measure of load, and you scale by adding more consumers. A topic has 12 partitions, so up to 12 instances of one service can share the work. Each topic also has a .dlq twin (see 2e). Automatic topic creation is turned off so a typo cannot create a 1-partition topic by accident.

HowTopics + KafkaTopicConfig create all topics at start-up with 12 partitions. Messages are keyed by the application id (or account id for profiles), so all events for one application stay in order. Retention was raised to 720 hours after the default 7 days silently deleted old events during a long pause.

2c. Transactional outbox

LogicA service never sends to Kafka directly. It writes the business change (e.g. "status = PARSED") and the event row into an outbox table in the same database transaction. A background "relay" reads unsent outbox rows every 500 ms (200 at a time) and publishes them to Kafka.

WhyWithout it there are two separate writes (database and Kafka). If the service crashes between them, either the event is lost or an event is sent for a change that never happened. With the outbox both succeed or both fail together. The relay may send a message twice after a crash ("at least once"), which is fine because consumers are idempotent (2d).

HowOutboxPublisher (writes the row) and OutboxRelay (@Scheduled(fixedDelay = 500), BATCH = 200, SELECT … FOR UPDATE SKIP LOCKED). SKIP LOCKED lets many relays run at once without two of them picking the same row. Production alternative: Debezium change-data-capture (no polling).

2d. Idempotent consumers (processed_events)

LogicBefore handling an event, a consumer checks the processed_events table for (consumer name, event id). If it is there, the event is skipped. If not, the work and the "processed" row are saved in one transaction.

WhyKafka and the outbox can both deliver the same message twice. Doing the work twice could, for example, double a penalty. The ledger makes a repeat harmless. It also makes "replay" safe: you can rewind a consumer to the start and it only redoes what you deleted from the ledger. This is how everyone was re-scored after the fairness fix (section 3i), without editing any score by hand.

HowProcessedEvents in ats-common. The indexer is the one exception: it always re-reads the current state from Postgres, so a duplicate just writes the same document again.

2e. Retries and dead-letter queues (DLQ)

LogicIf handling fails, Kafka retries it (several tries with a back-off). If it still fails, the message goes to <topic>.dlq with the error in its headers. A DLQ listener then marks the application with a clear status, e.g. PARSE_FAILED, and records the reason in the audit trail.

WhyOne broken file must never block the queue for everyone behind it, and it must not disappear silently either. The seeder plants one corrupt PDF on purpose (valid %PDF magic bytes, broken body) to prove this path works: exactly one DLQ message per 20 seeded resumes.

HowEach worker has a …DlqConsumer (e.g. ResumeUploadedDlqConsumer). Matcher, fraud and dedup share resume.extracted.dlq, so each DLQ listener filters on the original consumer group header.

2f. Database and migrations

LogicFlyway runs SQL migrations V1 to V12 at start-up (V12 is on the C2 branch). Hibernate never changes the schema (ddl-auto=none).

WhyThe schema is versioned in git, repeatable on any machine, and Flyway's lock lets several services start at the same time safely.

HowKey design: the scores row is written by three services, each owning its own column: matcher → match_score, fraud → fraud_penalty, rerank → rerank_adjustment. Postgres computes final_score as a generated column, and the JPA entity Score is @DynamicUpdate (it only writes the columns that changed). So the three services can write in any order without overwriting each other (V5).

2g. File storage with presigned uploads

LogicThe API gives the browser a short-lived (10-minute) signed URL. The browser uploads the file straight to MinIO. Then it calls /complete, and the API checks the file (size ≤ 10 MB, "magic bytes" say it is really a PDF/DOCX/PNG/JPG, computes SHA-256) before recording it and emitting resume.uploaded.

WhyResume bytes never pass through the API, so the API stays light even with thousands of uploads. Checking magic bytes (not the file name) stops a renamed .exe. The SHA-256 is reused later to catch the same file uploaded under another name.

HowUploadedFiles (shared by application and profile uploads), FileTypes, S3Config. The URL is signed for S3_PUBLIC_ENDPOINT (localhost:9000) because the signature includes the host name the browser actually uses. /complete is idempotent: calling it twice returns the same row, and keys outside the application's own folder are refused.

2h. Live updates (Server-Sent Events)

LogicThe API listens to application.scored and pushes each new score to every open dashboard over SSE (a long-lived HTTP response). A heartbeat every 25 s keeps the connection open.

WhyNew candidates appear in the table without refreshing or polling. SSE is simpler than WebSockets because data only flows server → browser. The UI reads SSE with fetch, not EventSource, because EventSource cannot send the sign-in token header, and tokens must not go into URLs (they would end up in nginx logs).

HowScoredEventsListener → SseHub (consumer group api-sse, latest offsets, no ledger because a duplicate push is harmless). nginx is configured not to buffer the stream. C2 adds ProfileSseHub, grouped per account.

3. Part 1: the recruiter side

3a. Apply & upload (Phase 2)

LogicFour public calls: create a candidate (POST /api/candidates), apply to a job (POST /api/jobs/{id}/applications, status APPLIED + application.created), get an upload URL, then complete the upload.

WhyApplicants should never need an account to apply. Keeping the apply flow public also lets tools/seed.sh drive the real API end to end.

HowIntakeController, ApplicationController, ResumeController/ResumeService. Files go to resumes/{jobId}/{appId}/v{n}/resume.{ext}. The synthetic resume generator (tools/generate_resumes.py) runs in a throwaway python:3.12-slim container (there is no host Python). At N ≥ 10 it plants 1 corrupt file and fraud cases; about 18% of resumes are image-only to exercise OCR. SEED=42 reproduces a batch exactly.

CheckedSeed 20 → 20 APPLIED, 20 MinIO objects, 20 resume.uploaded, outbox 40/40 published.

3b. Parser: PDF, DOCX, OCR and hidden text (Phase 3)

Logic

  1. Download the file from MinIO and detect its real type from magic bytes.
  2. PDF → PDFBox extracts text. A custom text stripper records every character's font size and fill colour.
  3. If a page has fewer than 100 characters, it is probably a scanned image: render it at 200 DPI and read it with Tesseract OCR; save the average word confidence.
  4. DOCX → Apache Tika.
  5. Save parsed.json (text + layout stats + a sample of hidden text) next to the resume, set status PARSED, emit resume.parsed.

WhyResumes come in many shapes, so the parser has a fallback for each. Recording font size and colour catches keyword stuffing: people hide words in white or 1-pt text so a machine sees them but a human does not. Only the parser image carries Tesseract, so the other images stay small.

HowDocumentParser (routing), PdfExtractor, LayoutCapturingStripper / LayoutStats, OcrEngine (finds the tessdata folder at runtime because Ubuntu moves it), DocxExtractor, ParseRecorder. max-poll-records: 20 so a batch always finishes inside Kafka's 5-minute limit.

Bug found later (Phase 6): PDFBox 3 does not track fill colour by default, so white text was never counted. Fixed by registering the six SetNonStroking* colour operators in the stripper.

CheckedSeed 20 → 19 PARSED + 1 PARSE_FAILED (the planted corrupt file), 16 via PDFBox + 3 via OCR (mean confidence 94.2), exactly 1 DLQ message, a 378-character hidden-text sample captured.

3c. Extractor: LLM → structured profile (Phase 4)

Logic

  1. Send the resume text to an LLM with a strict JSON schema: contact, skills, work history with dates, projects, education, certifications.
  2. Validate the answer against the schema. If it is invalid, retry once with the error message. If it is still invalid, try the stronger fallback model (gpt-oss-120b).
  3. Recover missing e-mail / phone with regular expressions.
  4. Normalise skills through a 150-entry taxonomy (aliases like "k8s" → kubernetes, plus each technology's first-release year). Unknown spellings go to unmatched_skills.
  5. Compute in Java, not in the LLM: total experience months (overlapping jobs counted once), seniority, completeness.

Why

  • Never trust the LLM: it can return broken JSON, make up numbers or be manipulated. The prompt says the resume text is data, not instructions (defence against prompt injection), and all arithmetic is done in code because LLMs are bad at maths.
  • Pluggable provider (LLM_PROVIDER=ollama|groq|gemini): one stubborn resume that failed on two models was rescued by a third. Model names are configuration, because providers retire them (two of them 404'd during the build).
  • Rate limits are back-pressure, not failures: on a Groq 429 the client waits for the time the server says, then tries again. Network/DNS failures are waited out (2-4-8-16-30 s).
  • Rules for load tests only: the Groq free tier allows about 1,000 calls a day, so the 10K load-test resumes (load_test = true) are read by RuleExtractor. Every real upload uses the LLM.

HowProfileExtractor, ProfilePrompts, ProfileValidator, RuleExtractor, LlmClient with GroqClient / OllamaClient / GeminiClient, LlmHttp, SkillTaxonomy, ExperienceMath. max-poll-records: 1 because one LLM call can take a long time.

Checked19/19 profiles extracted; unit tests for the maths. A real 4.2K-character resume that broke the small model's JSON mode was re-uploaded and logged "retrying once with openai/gpt-oss-120b", then scored 60.1.

3d. Scoring engine (Phase 5)

LogicSix components, each from 0 to 1, blended with weights, then limited by must-have skills:

ComponentHow it is computedDefault weightFresher job
skill_match70% must-haves (each weighted by recency) + 30% nice-to-haves0.350.35
experience_fitmonths ÷ required months, capped at 1.0 (full marks at and above the bar)0.250.05
projectsbest Jaccard overlap between a project's words and the job's skills, × 4, capped at 10.150.25
educationdated degree 1.0, undated 0.6, none 0.10.100.15
certifications2+ → 1.0, one → 0.7, none → 0.30.050.08
resume_qualityprofile completeness0.100.12
recency of a must-have skill = 1.0 if used ≤ 1 year ago, 0.8 if ≤ 3, 0.6 if ≤ 5, else 0.4
                               0.7 if only listed in the skills section (real but unproven)
cap         = max(0.2, 1 − 0.25 × number_of_missing_must_haves)
match_score = 100 × weighted_blend × cap
knock-out   = experience below half the bar → score limited to 15 (shown, never hidden)
              (fresher-friendly jobs never knock out on experience)
final_score = match_score − fraud_penalty + rerank_adjustment   (generated by Postgres)

Why

  • Explainable: each component comes with "evidence chips" (e.g. "kafka (recent)", "2 missing must-haves cap the score at 50%"), so a recruiter can see why someone ranks where they do.
  • Recency decay: a skill used last year matters more than one used eight years ago.
  • Cap, not just subtract: a candidate missing core skills should not reach the top just by being strong elsewhere.
  • Never hidden: even a knocked-out candidate stays visible at the bottom; a human decides.
  • Fresher-friendly weights: for graduate jobs, the experience weight moves to projects and education.
  • More experience is never a minus (see the fairness fix in 3i).

HowScoringEngine (pure function: profile + job → ScoreCard, no database), JobRequirements, ScoreRecorder. Pure means it is easy to unit test and can later move to ats-common so the candidate side uses the exact same code (planned for C4).

Checked24/24 scored (top 88.55 with full breakdown); tests assert the cap, the knock-out and that more experience never lowers the score.

3f. Trust Service: fraud checks (Phase 6)

LogicEach check returns flags with a weight (how strongly it suggests fraud):

FlagRuleWeight
HIDDEN_TEXT≥ 20 invisible characters (tiny or white text)0.7
TECH_ANACHRONISMa technology used before its first release year0.6
DUPLICATE_FILEsame SHA-256 under another name0.6
OVERLAPPING_JOBStwo full-time jobs overlapping more than 3 months0.5
IMPOSSIBLE_EXPERIENCEclaims more months than passed since graduation (+6 months grace)0.5
COPIED_CONTENT≥ 70% of work history matches another resume (from dedup)0.5
DISPOSABLE_EMAILthrow-away inbox domain0.3
REPEAT_APPLICANTsame e-mail / phone applied before (a note only)0
fraud_score   = 1 − Π (1 − weight)          ("noisy-OR": two 0.5 signals → 0.75, never above 1)
fraud_score ≥ 0.5 → status FLAGGED_FOR_REVIEW, fraud_penalty = fraud_score × 50

Why

  • Noisy-OR treats each signal as independent evidence: several weak signals add up, but the score can never pass 1. Signals below 0.5 are shown to the recruiter but cost nothing.
  • Thresholds measured, not guessed: honest claims sat at least 4 months under the graduation line, fakes 8 months over it.
  • Flags never overrule humans: the system only flags. A recruiter clears (points come back) or confirms (rejected). Status only moves from EXTRACTED/SCORED; SHORTLISTED/REJECTED are never touched. A clearance survives re-checks unless genuinely new weighted evidence appears. Nothing is auto-rejected.

HowTrustCheck interface with HiddenTextCheck, TimelineCheck, AnachronismCheck, DisposableEmailCheck, DuplicateCheck; TrustScorer (FLAG_THRESHOLD = 0.5, MAX_PENALTY = 50); TrustRecorder; FraudReviewController for the Review Queue.

CheckedEvery planted type flagged with its explanation; on the 34 existing resumes exactly the 6 planted fakes were flagged, and the former top 4 (all fakes, boosted by hidden keywords) dropped out of the lead; 33 fraud tests.

3g. Deduplication: MinHash + LSH (Phase 6)

Logic

  1. Same e-mail or phone → REPEAT_APPLICANT note. Same SHA-256 → DUPLICATE_FILE.
  2. For copied work history: split title + company + description into 5-word "shingles".
  3. MinHash squeezes the shingle set into 128 numbers. The share of equal numbers between two resumes estimates how much text they share (Jaccard similarity).
  4. LSH cuts the 128 numbers into 32 bands of 4. Two resumes become candidates only if a whole band matches, so a new resume is compared with the few in its buckets, not with all 500K.
  5. Verify candidates at ≥ 0.70 similarity → COPIED_CONTENT, and both resumes share a cluster id.

WhyComparing every resume with every other is n² work, impossible at 500K. MinHash + LSH make it close to constant per resume. The 0.70 cut-off is far above the most similar honest pair in the data (0.12). Both sides of a match are flagged on purpose: the system cannot know who copied whom, so a human clears the original once.

HowMinHash (fixed seed so results are repeatable), Lsh, DuplicateFinder, DedupRecorder. Results flow to the Trust Service as application.deduped. Known limit: heavy rewording of a short resume can fall below 0.70.

3h. Embeddings & hybrid search (Phase 7)

Logic

  1. Embedder: turns each profile into 768 numbers that capture its meaning (Ollama nomic-embed-text), stored in pgvector. Texts about the same topic land close together even with different words.
  2. Indexer (CQRS read model): on every change event it re-reads the candidate from Postgres and writes a search-shaped document to OpenSearch, in batches of up to 500 events or 2 seconds.
  3. Search: runs keyword search (BM25) and meaning search (kNN) side by side with the same filters (skills, minimum experience, hide flagged), then merges them with Reciprocal Rank Fusion.
RRF score = 1/(60 + keyword_rank) + 1/(60 + semantic_rank)     (a list it is missing from adds 0)
Each result is labelled: keyword, semantic or both.

Why

  • Hybrid because each method alone fails: keywords miss synonyms ("event driven" vs "Kafka"), and on this templated data meaning scores bunch together at 0.50–0.65, so meaning alone is weak.
  • RRF uses positions, not scores, so the BM25 and cosine scales never have to agree. k = 60 stops rank 1 from drowning everything else.
  • Keyword min-match "3<75%": measured, OR matched 44/53 (everyone says "backend") and AND only 14.
  • CQRS: search reads a copy shaped for searching; Postgres stays the single truth. Because the indexer re-reads the truth, duplicate or out-of-order events cannot corrupt the copy. Rebuild = rewind the indexer.
  • Degrade, don't break: without Ollama, search answers keyword-only and says so; without OpenSearch it returns a clear 503 and the rest of the API keeps working.
  • nomic needs search_document: / search_query: prefixes, so EmbeddingClient exposes embedDocument / embedQuery and no caller can forget. keep_alive: 24h stops Ollama unloading the model (the cold reload took 4.1 s).

Howembedder-service (ProfileText, EmbeddingRecorder), indexer-service (ChangeEventsConsumer, CandidateDocuments), API SearchController, SearchQueries, HybridRanker (K = 60).

Checked"event driven backend" returns Aditya Joshi labelled semantic: his profile mentions Kafka but never "event driven" (checked in SQL). 53 docs = 53 profiles.

3i. AI rerank & the fairness guard (Phase 8)

LogicPOST /api/jobs/{id}/rerank sends the top 50 candidates to the stronger model as compact "evidence cards", 5 per call. For each it returns a 3-line summary, must-have coverage, depth vs breadth, red flags and a score nudge of at most ±10%. It runs in the background and streams results to the page.

WhyA formula cannot read nuance the way a senior recruiter does; the LLM adds a second opinion. But it may only nudge: the ±10% limit is enforced in code and by a database CHECK constraint, so even a bug cannot let the AI rewrite the ranking. 5 per call because 10 per call got answers cut off (only 17–24 of 50 judged).

The fairness story. The model kept writing "overqualified — flight risk". Prompt fixes barely helped, because the bias came from our own formula: since Phase 5 the matcher lowered experience fit for anyone with 3× the required experience and printed that label. Experience correlates with age, so this is an age-discrimination proxy. It hit 263 of 359 candidates. Fix: the penalty was removed (a test now asserts more experience is never a minus); everyone was re-scored by replaying Kafka (no hand-edited scores); old verdicts were cleared; and the rerank now discards any verdict that relies on such a proxy (the candidate keeps the formula score). The re-run had 0 bias discards.
Lesson: when an AI repeats a bias, check what you fed it before tuning the prompt.

HowRerankController, Reranker (BATCH = 5), RerankCards, RerankPrompts, RerankRecorder, migration V9. One full rerank uses about 35–40K tokens against a 200K tokens/day limit, so it is run once per demo.

3j. 10K load test & scaling lessons (Phase 8)

Logic./tools/seed.sh --bulk 10000 renders 10,000 PDFs (~40 s on all cores) and 20 parallel workers push them through the real API. Then docker compose up -d --scale parser=8 --scale extractor=4 and watch the lag drain.

Measured10,000 submitted in 676 s with 0 API errors; backlog 2,927 → 0; 10,369 applications processed, 57 flagged, 7 parse-failed (planted); search index 10,362 docs.

What it taught

  1. Database connections ran out. 8 parsers + 4 extractors × default pool 10 ≈ 190, Postgres allowed 100. Fix: worker pools of 4, Postgres max 200. Production: PgBouncer.
  2. The parser never committed progress. 500-record batches outlived Kafka's 5-minute poll interval, so Kafka kicked the worker out mid-batch. Fix: max-poll-records: 20.
  3. Partitions cap parallelism. The leftover work sat in 4 of 12 partitions, so 4 of 8 parsers idled.
  4. The laptop was CPU-bound (~15 of 16 cores busy). Honest result: no clean 8× speed-up on this machine (8 parsers ≈ 3.5/s vs 1 ≈ 3.3/s). DEMO.md describes how to measure it properly.

4. Part 2: the candidate side

Candidates get their own portal on the same pipeline and the same scoring engine, so nothing is scored two different ways. Built one phase at a time (C1 … C8). C1 is merged into main; C2 is complete on feat/candidate-profile.

4a. C1: accounts & sign-in

Logic

  • Two tickets. A 15-minute access token (JWT signed with HS256, sent as Authorization: Bearer, kept only in page memory) and a 7-day refresh ticket in an httpOnly, SameSite=Strict cookie visible only to /api/auth/*. The database stores only the SHA-256 of the refresh ticket.
  • Rotation + theft alarm. Each refresh replaces the ticket. If an already-replaced ticket comes back, someone copied it, so every ticket of that user is cancelled. The row is locked (SELECT … FOR UPDATE) so two simultaneous refreshes run one after another.
  • Roles: CANDIDATE, RECRUITER, ADMIN. Public: /api/auth/**, health, skills list, the Part 1 apply flow. /api/candidate/** → CANDIDATE. Everything else → recruiter-only by default.
  • E-mail verification: a one-time link (32 random bytes, only the hash stored, 24 h). Mailpit catches the mail locally.
  • Account claim: once verified (and at every later sign-in), earlier applications with the same e-mail are linked to the account. @intake.invalid placeholders can never be claimed.
  • Per-IP rate limits: sign-in 10/min, sign-up 5/10 min, resend 3/10 min → HTTP 429 with Retry-After.
  • Ownership: a candidate can only read their own applications; someone else's answers 403. The caller id always comes from the signed token, never from the request.
  • Neutral statuses: candidates see Received / In review / Not selected / "We couldn't read your resume". A fraud flag looks exactly like any other review.

Why

  • Short access tokens limit the damage if one leaks; the refresh cookie cannot be read by JavaScript (protects against XSS) and is not sent cross-site (protects against CSRF). Storing hashes means a database leak does not leak working tickets.
  • Recruiter-only by default means a forgotten rule fails safe.
  • Claim only after verification, because anyone can type any e-mail into a public form.
  • Neutral statuses: showing FLAGGED_FOR_REVIEW would tip off a cheater. The mapping is an exhaustive switch with no default, so a new pipeline status will not compile until someone decides what candidates see.
  • Sign-in says "wrong email or password" for both cases, and checks a dummy BCrypt hash for unknown e-mails, so even the response time does not reveal which accounts exist.
  • The UI serialises refreshes across browser tabs with the Web Locks API; otherwise two tabs refreshing at once would look like theft and sign everyone out.
  • Spring Security's own JWT support (Nimbus) was used, so no third-party JWT library was added.

4b. C2: master profile & profile resume

Logic

  1. A candidate uploads a resume for themselves, not for a job, to profiles/{account}/v{n}/, with the same checks as application uploads.
  2. It flows through the same parser and extractor on its own topics: profile.resume.uploaded → profile.resume.parsed → profile.changed → profile.embedded.
  3. One profile per account, rebuilt from each new version.
  4. The candidate can fix the result: add/remove skills and correct job dates. Fixes are stored apart from what was read (profile_overrides), so a re-upload never wipes them. Date fixes are keyed by lower-case "company|title", so they survive a re-parse that lists jobs in another order.
  5. Effective profile = what was read + the fixes, with months, seniority and completeness recomputed. It is what the page shows, what gets embedded, and what later phases read.
  6. The "My Resume" page follows Uploaded → Read → Profile built → Searchable live over SSE.

Why

  • Separate topics, because resume.extracted already has four application-only readers (matcher, fraud, dedup, embedder). On a shared topic each would look for an application that does not exist and fill the DLQ. With separate topics those services did not change at all.
  • Subject in the envelope (subject_type, subject_id) so every event says what it is about. Older events without it are read as APPLICATION, so nothing breaks.
  • One profile per account, not per candidate row: candidate rows are one per application (one person had 4 rows).
  • Two safety rules: a failed upload never wipes a good profile, and an older version's late answer never replaces a newer one. The late-version test was proven by deleting the guard for one run.
  • One shared function (EffectiveProfile) so no screen or service sees a different profile. For that, ExperienceMath moved from the extractor into ats-common (same code, same tests).
  • Profile resumes always use the LLM: it is a real person's resume, never load-test data.
  • Failures speak plainly to the candidate ("We couldn't read this file — if it's a scan, try a clearer copy"); technical causes stay in the logs.

HowAPI: ProfileController, ProfileResumeService, ProfileOverridesService (PUT /api/candidate/profile/overrides; 400 for bad dates or an unknown role, 409 before anything was read), ProfileEventsListener + ProfileSseHub.
