- **2026-10-25 · C1 batch 1b — e-mail verification, account claim, limits, ownership**: (a) **Mailpit** (`axllent/mailpit:v1.31.6`, UI + REST API on :8025) catches every e-mail; the API sends SMTP to `mailpit:1025` with 3 s timeouts (JavaMail's own default waits forever) and no `depends_on` — a stopped Mailpit only loses the mail, sign-up still works and `POST /api/auth/resend-verification` (signed in, 3 per 10 min per IP) mails a new link. Mail goes out after the link row is saved, never inside a transaction. (b) **Verify link**: 32 random bytes, only the SHA-256 stored (V11 `email_verifications`), valid 24 h, works once; a second click is a harmless no-op. (c) **Account claim** runs when the link is opened and again at every sign-in of a verified candidate (so later public applications with the same e-mail show up): `UPDATE candidates SET user_id … WHERE lower(email) = … AND user_id IS NULL AND email NOT LIKE '%@intake.invalid'` (uses the lower(email) index). Before verification nothing is linked; recruiters never claim. Sign-ups with an `@intake.invalid` address are refused — Mailpit accepts mail for any address, so a placeholder could otherwise be "verified". (d) `Candidate.userId` is mapped **read-only** in JPA: the extractor saves whole Candidate rows and would otherwise write back a stale NULL over a claim. (e) **Rate limits per IP** (fixed window, in memory — one API instance, no Redis): sign-in 10/min, sign-up 5/10 min, resend 3/10 min; the next attempt gets 429 with `Retry-After`. nginx now passes `X-Real-IP`; a request straight to :8082 is keyed by its socket address (documented: the API port is not meant to be public). (f) **Ownership**: `GET /api/candidate/applications` (mine — the claimed rows) and `/{id}`, where someone else's or an unclaimed application answers 403; the caller id always comes from the signed token. `OwnershipTest` runs through the real filter chain and was checked by deleting the ownership check for one run (2 tests failed: expected 403, got 200). (g) Log lines mask e-mails (`p***@gmail.com`). (h) **Verified live 2026-10-25**: V11 applied in 0.05 s; signed up with the (synthetic) e-mail of seeded candidate Sanjay Joshi → 201 unverified, Mailpit held 1 "Verify your e-mail for ATSPipeline" with the link; my applications before opening it `[]`, after it 1 (Graduate Software Engineer, SCORED) and his own `/{id}` 200; same link again 200 (no second claim), a made-up link 400; `a@test.dev` reading his application 403 and her own list `[]`; resend for `a@test.dev` 204 (Mailpit 0 → 1), for the verified account 409, without a token 401; `@intake.invalid` sign-up 400; DB: 1 link, used, 64-hex hash, 1 candidate row linked; Mailpit stopped → sign-up still 201 in 3.3 s with the masked log line; the 11th sign-in within a minute → 429 `Retry-After: 48`. Part 1 smoke: `seed.sh 1` → Sneha Singh SCORED ~6 s after submit, her new row unclaimed (`user_id` NULL). Tests: api-service 65/65 (20 new), ats-common 16/16.

- **2026-10-24 · C1 batch 1a — sign-in**: (a) Spring Security with its own JWT support (`spring-boot-starter-oauth2-resource-server`, Nimbus; Spring Security 6.5.11 from the Boot BOM) — no third-party JWT library. HS256 signed with `JWT_SECRET` (32+ bytes, generated into the gitignored `.env`); the API refuses to start without it. (b) Access token 15 min, claims `sub` (user id) + `roles` only — no email or name in a token anyone holding it can read. Refresh token 7 days: 32 random bytes in an httpOnly, SameSite=Strict cookie scoped to `/api/auth`; only its SHA-256 is stored; rotated on every use. A reused (already cancelled) ticket cancels every ticket of that user — `noRollbackFor` keeps that cancel despite the 401 — and the row is locked (`SELECT … FOR UPDATE`) so two simultaneous refreshes run one after the other. (c) The UI keeps the access token in memory only and serialises refreshes across tabs with the Web Locks API; without that, two tabs refreshing with the same cookie would look like theft and sign everyone out. (d) CSRF protection is off on purpose (bearer header + SameSite=Strict cookie); the cookie's `Secure` flag is configurable and off for the plain-http localhost demo. (e) Access rules: public = `/api/auth/**`, health, `GET /api/skills` and the Part 1 apply flow (so applicants never need an account and `seed.sh` is unchanged); `/api/me` = any signed-in user; `/api/candidate/**` = CANDIDATE; everything else = RECRUITER/ADMIN, so a new endpoint is recruiter-only by default. ASYNC/ERROR dispatches are permitted: SSE completions and error pages re-enter the filter chain after the request was already checked. (f) Sign-up always creates a CANDIDATE (the role is never read from the request); a duplicate email gets 409 (this reveals that the email has an account — accepted for the demo). Sign-in answers "wrong email or password" in both cases and compares against a dummy BCrypt hash for unknown emails, so timing does not tell them apart either. Passwords: ≥10 characters, ≤72 bytes (BCrypt reads only 72). `users.email` is stored lower-case under a CHECK, so a plain UNIQUE index is case-insensitive and serves the sign-in lookup. (g) Sign-out cancels the refresh ticket at once; an access token keeps working until it expires (≤15 min) — the price of not looking tokens up per request. (h) The demo recruiter is created at startup from `RECRUITER_EMAIL` / `RECRUITER_PASSWORD` (never hard-coded); an existing account is left alone. (i) The UI reads SSE through `fetch` instead of `EventSource`, which cannot send an Authorization header — no tokens in URLs or nginx logs. (j) First Spring web-slice test in the repo (`@WebMvcTest` + `@MockitoBean`): access rules have to be tested through the real filter chain. The 403 test was checked by weakening the recruiter rule for one run — it failed as it should (expected 403, got 200). (k) Docs: `curl` calls to recruiter endpoints now need a token (DEMO.md "Recruiter token"). (l) **Verified live 2026-10-25**: V10 applied in 0.17 s, recruiter seeded; 19 curl checks — sign-up 201 (CANDIDATE, unverified, 900 s token), `/api/me` 200 own account, recruiter endpoint 401 without token / 403 with a candidate token / 200 with the recruiter's, cookie `HttpOnly; SameSite=Strict; Path=/api/auth; Max-Age=604800`, refresh 200 then the old cookie 401 and the rotated one 401 (theft alarm), sign-out 204, duplicate e-mail in another case 409, short password 400, wrong password and unknown e-mail both 401 "wrong email or password", a sign-up asking for ADMIN got CANDIDATE; DB: refresh tokens stored only as 64-hex SHA-256. Browser (headless Chrome): sign-in page when signed out, wrong-password message, dashboard after sign-in, a reload of `/candidates` restored the session from the cookie (10,369 of 10,369 rows), and the job page's token-carrying stream (HTTP 200) applied pushes live — a row went `applied` → `scored 36`, and a candidate seeded after the page opened appeared (4 → 5 rows). `seed.sh 1` (public apply flow) unchanged.

- **2026-10-19 · Bias fix — "overqualified / flight risk" removed (a Phase 5 mistake)**: since Phase 5 the matcher cut `experience_fit` from 1.0 to 0.8 for anyone with 3× the required experience and added the red evidence chip "heavily overqualified — flight risk" (with a unit test asserting it). That is an age-discrimination proxy: experience correlates with age. It hit **263 of 359** Backend Engineer candidates, and the Phase 8 LLM rerank then read the chip from the evidence cards and repeated it (17 biased verdicts in one run, still after prompt fixes). Fix: more experience is never a minus (full marks at and above the bar; the test now asserts it); every candidate re-scored by replaying the matcher (ledger cleared + offsets rewound — no hand-edited scores): the 263 rose (avg match 26.82 → 29.06), nobody else changed, all 33 flags / 2 rejections untouched, 0 candidates still labelled. All 45 rerank verdicts made with the biased evidence were cleared (RERANK_CLEARED audit). The rerank keeps its own guards (positive instructions, minimum labelled a floor, bias-proxy verdicts discarded whole, unjudged candidates reset). Lesson: an AI repeating bias usually means OUR data fed it the bias — check the inputs before tuning the prompt. **Groq note**: gpt-oss-120b has a 200,000 tokens/day limit; one full rerank ≈ 35–40K tokens.

- **2026-10-17 · Phase 7 notes**: (a) **Measured before building**: nomic-embed-text gives 768 dims at ~0.27s/doc on CPU (10K resumes ≈ 45 min — Phase 8 must plan for it); on the templated synthetic data cosine scores bunch at 0.50–0.65, so semantic alone is weak and hybrid is essential. The whole-profile text beats dropping the summary (semantic hit at rank 3 vs 9). (b) **nomic prefixes**: documents and queries must be embedded as `search_document:` / `search_query:` — `EmbeddingClient` exposes `embedDocument`/`embedQuery` so no caller can forget. (c) **Keyword min-match measured**: OR matched 44/53 for "event driven backend" (everyone says "backend", labels meaningless), AND matched 14 → `minimum_should_match: "3<75%"`. (d) **RRF k=60 client-side**, depth 50 per list; one shared filter list feeds both BM25 and the Lucene-engine filtered kNN. (e) **CQRS read model**: the indexer re-reads Postgres for every changed application (events carry ids only), so duplicates/out-of-order events are harmless and no ledger is needed; the 500-or-2s batch window is Kafka's own (`max-poll-records 500`, `fetch-max-wait 2s`, `fetch-min-size 1MB`) — first replay packed 115 events into one 52-doc bulk request. Recovery after an OpenSearch outage = reset the `indexer-service` group's offsets to earliest and let it rebuild. (f) **Keyword stuffing pollutes search**: the LLM extracts hidden-text keywords as skills, so stuffers match words they hid — results carry status + fraud score (shield badges) and `hideFlagged` is an opt-in filter (flags never hide by default). (g) **Ollama unloads idle models after 5 min**; the cold reload (4.1s measured) made the first search after a break keyword-only → `keep_alive: 24h` on every embed call. (h) Graceful degradation: no Ollama → keyword-only with `"semantic":"unavailable"`; no OpenSearch → 503 with the start command; the rest of the API is unaffected. (i) `docker compose --profile search up -d` brings up OpenSearch, Ollama + `ollama-init` (pulls the model), `opensearch-init` (template + index), embedder and indexer. - **2026-10-15 · Phase 6 notes**: (a) **Parser bug found before building**: PDFBox 3's `PDFTextStripper` registers no fill-colour operators, so `nearWhiteChars` was always 0 (Phase 3 note (e) explained). Fixed by registering the six `SetNonStroking*` operators; resumes parsed since read "tiny white text", older parsed.json files still say "smaller than 4pt" (not re-parsed). (b) **V5 split score ownership**: `match_score` (matcher) + `fraud_penalty` (Trust Service), `final_score` a Postgres GENERATED column, `Score` is `@DynamicUpdate` — two services write one row in any order without erasing each other's half. (c) **Trust policy**: five checks (timeline overlap >3 months between full-time roles; claim > months since June of graduation +6; tech used before its first release; ≥20 invisible chars; disposable email; dedup findings), combined by noisy-OR `1 − Π(1 − w)`; ≥0.5 → FLAGGED_FOR_REVIEW + penalty = score × 50; soft signals below 0.5 are shown but cost nothing. Thresholds were measured on the real data before review: honest claims sit ≤ −4 months from the graduation line, fakes +8. (d) **Flags never overrule humans**: the status moves only from EXTRACTED/SCORED; SHORTLISTED/REJECTED are never touched; a human FRAUD_CLEARED **sticks** across re-checks unless a NEW weighted kind of evidence appears. (e) **Dedup**: MinHash (128 perms, fixed seed, 5-word shingles over title+company+description) + LSH 32×4 + verification at ≥0.70; the most similar honest pair in the data is 0.12. Same email/phone = REPEAT_APPLICANT note (0), same file under another name = DUPLICATE_FILE (0.6), ≥70% work history = COPIED_CONTENT (0.5). (i) **Frontend containerized** (nginx on :5174, `/api` proxied, SSE unbuffered) and every service is `restart: unless-stopped`, so a reboot no longer needs manual restarts.
